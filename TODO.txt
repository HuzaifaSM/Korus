MYTHIC AFFIX REWORK:
  - STATUS: content done (scripts/items/mythicAffixes.json, 110 affixes), Python-side wiring NOT started
  - goal: mythic affixes should be rule-breaking/build-defining like PoE uniques, not stat sticks. soulbound affixes stay as 'same stats but bigger numbers', mythic becomes the 'mechanic-altering' tier
  - architecture (finalised, differs from the old plan in one big way - dedicated field, not extra prefix/suffix slots):
    > 1 mythic affix per mythic item, no more - stored in its OWN field on Equipment (same pattern as self.destabilisedAffixes), NOT a normal prefix/suffix slot and not consuming one
    > a mythic affix can carry MULTIPLE "lines" (effects) from one roll - same idea as an implicit being 'one roll' that can still produce multiple stat lines. e.g. one affix might grant an ability AND a flat stat, or three simultaneous stat swings from a single roll
    > guardrail: no PERMANENT scaling onto the PLAYER. Temporary/in-combat stacking is fine (resets naturally like any buff) - the guardrail is specifically about state that outlives combat AND survives unequip. Anything that needs memory is tracked as state ON THE ITEM (mirrors existing item-side state: entropy, mastery, numPreserved), never the player
    > mythic weapon affixes are NOT split into one_handed/weapon(2h) pools like normal affixes - a single "weapon" bucket, with any handedness difference (e.g. 1.5x vs 1.2x one-handed) baked directly into the affix's own numbers/text instead
  - scripts/items/mythicAffixes.json (DONE - read this file directly for full content, all 45 slot-specific ideas + rationale live there now):
    > shape: {equipType: {affixId: {name, levelReq, categories, lines: [...]}}} - no prefixes/suffixes nesting, doesn't apply here
    > 10 top-level buckets: weapon, head, chest, legs, feet, ring, amulet, shield (not 'offhand' - matches the JSON_POOL_KEY convention already used in affixes.py), sigil_offensive, sigil_defensive
    > each line has "effect" (a key the future registry dispatches on) + "text" (templated with [x]/[y]/[z] placeholders) + either "rolls" ([{key,min,max,isPercent}, ...]) for flat/ability lines, or a dedicated scale_with_item_level shape (stat, isPercent, perLevel:{min,max}, cap) for the "+X per Item Level, capping at 120" family that appears on every slot
    > no "weight" field anywhere - mythic affixes should all be roughly equally powerful, so rolling one is meant to be a plain random.choice(), not weighted like normal affixes
    > 2 universal affixes duplicated into all 10 buckets (bonus_prefix_slot, bonus_suffix_slot - roll +1/+2 extra affix slots; bonus_max_mastery - +8-12% max mastery on the item), same convention normal affixes.json already uses for identical affixes appearing in multiple equipType buckets
  - still to do (nothing started):

Effect keys already used in the JSON that need a handler: grant_ability, scale_with_item_level, negate_resistance_group, conditional_modifier, automatic_trigger, item_tracked_scaling, resource_conversion, damage_type_override, passive_conversion, hybrid_defense_conversion, block_chain, damage_reflect, crit_punish, ignore_stat_defense, ignore_unavoidable, implicit_multiplier, mastery_bonus, affix_slot_bonus

Fixed with a proper __deepcopy__ that builds through the constructor instead (same idiom _freeze() already uses). Relevant if any future mythic effect code needs to deepcopy a _stats dict.

    > maxEntropy = float('inf') - Equipment.__init__ already accepts an explicit maxEntropy override and entropyLocked/craftable are computed off entropy >= maxEntropy, so this already works correctly with zero other code changes needed
    > blank items must not roll entropy-related affixes (added_entropy, increased_entropy, entropy_resistance - confirmed exact affix IDs from affixes.json) since entropy is irrelevant until manually closed out. Fix goes in Equipment.getExcludedIds(): add those 3 ids to both excludedPre and excludedSuf when self.rarity == ItemRarity.BLANK (harmless to add to both regardless of which one they actually are)
    > durability/value should match or slightly beat Mythic's baseline (1100 durability, 2.5x value multiplier) - "should be similar rarity to strong legendary or mythic items"
  - the reveal + curated crafting flow:
    > before reveal: displayed as just the base item name (e.g. "Axe") with the thistle1 bold underline tint, not the normal rarity-name-affix naming pattern
    > reveal = the same action as opening the curated crafting session, not two separate steps - a "Reveal Blank Items" storage/menu option, selecting one both reveals it and opens crafting immediately
    > on opening: roll ONE of 5 curated tables (below), then roll a FIXED hand of runes from that table ONCE - not re-rolled per craft action, the player crafts freely within that fixed hand until they choose to finish
    > the offered runes are NOT drawn from the player's own rune inventory and are NOT consumed from it - bespoke/conjured for this item only, independent of what the player actually owns (this is why the guaranteed Destabilisation Rune can always be present regardless of inventory)
    > hand composition per table: 7-10 unique rune TYPES from that table's theme, several copies of each (quantity scaled by power - weak/safety runes get up to ~10 copies, a Perfect/Sovereign-tier rune might only get 1-2), PLUS always: 1 Destabilisation Rune (rolled Greater vs Perfect at an 80/20 split, but Perfect only if item.level >= 80, otherwise always Greater - Perfect's own minItemLevel=80 would otherwise silently fizzle), PLUS equal counts of the Overflowing Growth Rune and the Blank Erasing Rune (BOTH already exist as real runes - scripts/crafting/growthRune.py's OverflowingGrowthRune fills every empty slot at once, scripts/crafting/erasingRune.py's BlankErasingRune clears every affix at once - together they give a genuine fill-everything/clear-everything reset loop within the fixed hand)
    > the 5 curated tables (all map to REAL existing rune categories in runeDrops.py's ALL_RUNES - no new rune content needed, just curated bundling):
      - Cultivator's: Growth + Revealing heavy - safe, low-risk, ends with a full item
      - Chaosweaver's: Chaos + Fusion/Manipulation heavy - remix-heavy, iterate toward a specific combo
      - Artisan's: Manipulation (equilibrium/sacrifice) + a little Growth - precise, sequence-dependent
      - Seer's: mostly Revealing - maximum control, least RNG, probably the 'best' table
      - Anomalous: Rarity + Mastery + a couple Chaos/Randomiser - swings for value/mastery extremes over affix precision
    > two distinct ways to finish crafting and lock the item in:
      - SAFE exit: set maxEntropy = 0 (this alone makes entropyLocked immediately true, since entropy >= maxEntropy always holds once entropy has ticked up even slightly, which every normal rune application already does via item.addEntropy()) - does NOT set destabilised = True, no outcome roll, no risk. This is "not a TRUE destabilisation... only in name to prevent further modification"
      - GAMBLE exit: actually apply the guaranteed Destabilisation Rune from the hand - rolls the real outcome table (data/destabilisation.json), chance at eternal/transcendent, chance at brick. This DOES set destabilised = True and is the only path that shows the "DESTABILISED" tag
  - related bug found and NOT yet fixed (relevant since it's one of the two guaranteed safety-net runes in every hand): scripts/crafting/growthRune.py's OverflowingGrowthRune.apply() success path never calls item.update(), item._generateName(), or item.addEntropy() - unlike every sibling rune in the file. Right now this means the rune is free (no entropy cost) and leaves the item's cached stats/name stale until something else refreshes them. Should be a quick 3-line fix mirroring its siblings.
